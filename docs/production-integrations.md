# Muse: production integration setup

Implemented on 2026-10-10. Muse remains the name. The app starts free with the existing daily reset; only Premium increases the allowance. This code has not been deployed or connected to live provider/store accounts.

## What runs now

- **Trust enforcement:** Cloud Functions check the caller and other members before discovery, likes, solo swipes, Duo invitations/confirmation, Duo discovery/matching and calls. Swipes and Duo matches check within their Firestore transaction. Solo likes also rebuild both profiles’ current preferences, visibility and cohorts within that transaction, so stale cards cannot create unwanted contact. Firestore rules require current approvals for every participant before a message can be sent. Banned members cannot initiate contact, including in a closed verification preview. Reading an existing chat, reporting, blocking, unmatching, leaving a Duo, editing settings and deleting an account remain available.
- **Photo binding:** verification snapshots copy the exact Cloud Storage object generation into `verified-photos/{uid}/{attempt}/{index}`. Clients cannot create, replace or delete these objects. Approval replaces the profile photo list with the checked snapshots atomically with the server approval. Changing/reordering photos or reaching the 90-day expiry invalidates approval. Old URL-only approvals do not qualify.
- **Live check:** Didit hosted biometric authentication receives the first frozen profile photo as its reference. Its signed callback must report warning-free liveness and face matching. It leaves the account pending; a moderator must review **every** frozen photo against the live session, including generated/face-altered imagery, before approval. There is no claim that a provider or human review can detect every synthetic image. A photo check does not prove age, identity, intentions or safety.
- **Premium:** RevenueCat native SDK + server REST validation, fixed 24-hour/7-day/30-day consumable passes, signed webhook reconciliation, purchase-owner ledger, expiry/refund handling. Plus gives 100 likes and 5 Super Likes a day, priority likes and the age-gap filter; free stays at 25 likes and 1 Super Like. It shares the same daily counter, so buying/rechecking/restoring never resets spent likes. Safety, photo verification, basic matching, messaging and Likes You remain free.
- **AI:** both members must enable AI vibe matching in Settings. Claude gets only fixed catalog interests, vibes and dating intentions, indexed within that request. Names, account IDs, age, gender, location, photos, chats, bios, prompt text and the hidden casual preference are excluded. Scores can influence 20% of ordering among already eligible candidates. Reasons remain grounded in actual shared profile evidence. Missing consent, invalid output, timeout, no key or the 10-calls/day cap uses the existing ranking. It is not a relationship probability.
- **Calls:** the backend issues a five-minute, room-specific RS256 JaaS token only for an active match whose members pass verification. Recording, transcription and streaming permissions are disabled. Existing sessions are not forcibly disconnected by a later block; members can leave, and new access is denied. Calls need provider QA before enabling.

## Verification account and configuration

1. Create a Didit application and publish a **Biometric Authentication** workflow using live camera liveness and Face Match against `portrait_image`. Do not use a document-only KYC workflow; Muse does not need Aadhaar or another identity document for this photo check. Configure conservative attack/mismatch warnings and a short provider retention window; disable retained face templates. Test capture accessibility and failure/review cases with real devices before launch.
2. Put the published workflow ID and application ID in `firebase/functions/.env` as `DIDIT_WORKFLOW_ID` and `DIDIT_APPLICATION_ID`. Keep `MUSE_VERIFICATION_ENABLED=false` until callback, moderation and erasure QA passes.
3. Store `DIDIT_API_KEY` and the destination's `DIDIT_WEBHOOK_SECRET` using Firebase Secret Manager (`firebase functions:secrets:set NAME`). Never place these in mobile environment variables. The API key needs create-session and delete-session permissions.
4. Set the Didit destination to the deployed `diditWebhook` URL and subscribe to `status.updated`. Muse verifies the full V2 HMAC, signed timestamp (five-minute freshness), exact workflow/application, live environment and session/attempt binding. Console test webhooks and sandbox approvals do not create production badges. Older deliveries cannot overwrite newer decisions. A real live callback is still required for production acceptance testing.
5. Assign `moderator: true` as a Firebase Auth custom claim only to trusted operators. `getPhotoReviewQueue` exposes pending frozen profile photos to those operators. Review the live session in Didit's console, compare every photo and check authenticity. The review callable requires explicit all-photo/authenticity attestations and records reviewer/time/decision. Provide a monitored support inbox for appeals; a new successful check can follow a rejection. There is no staffed appeals queue provided by the code.

   The operator helper is `firebase/functions/scripts/photo-review.mjs`. Supply `GCLOUD_PROJECT`, `FUNCTIONS_REGION` and a current `MUSE_MODERATOR_ID_TOKEN` through your secure environment. Run with no arguments to list pending sessions, `--reject SESSION_ID` to reject, or `--approve SESSION_ID --reviewed-all-photos --authentic-photos` only after those checks. The helper never grants moderator claims. `--emulator` is limited to `demo-*` projects.
6. The scheduled `cleanupPhotoChecks` erases provider sessions and biometric templates after adjudication or the 24-hour review window, on a daily run (up to roughly 48 hours from creation within the job’s 100-session/day capacity; backlogs or outages can delay this). Failed erasure is retried. Account deletion requests provider privacy erasure before removing session records and all frozen photos. Provider outages can delay account erasure; support must handle retries and monitor the job. Configure provider-side maximum retention as a backstop for network failures during session creation.
7. Missing `runtime/trust` defaults to **verification required** in both backend and security rules. Production should use `{requireVerification: true}` or no document. Only admins can change it. The emulator seed explicitly sets false for closed UI fixtures; never copy that exception to a public environment. Capture configuration and enforcement are separate: disabling capture does not silently remove the trust requirement.

Primary references: [Didit session API](https://docs.didit.me/sessions-api/create-session), [V2 callbacks](https://docs.didit.me/integration/webhooks), [privacy erasure](https://docs.didit.me/sessions-api/delete-session).

## Web payments (Razorpay)

Paire Plus on the web uses Razorpay. Setup, variables and the webhook are in [launch-web.md §2](launch-web.md#2-razorpay-paire-plus-on-the-web). The flow: `createPlusOrder` (server price, server-only `razorpayOrders/{orderId}`) → Razorpay Checkout → `confirmPlusPayment`. That step checks the HMAC of `order_id|payment_id`, then re-reads the payment from the Razorpay API (captured, same order, amount and currency) before granting the pass once. `razorpayWebhook` (HMAC of the raw body) covers late captures and `refund.processed`. Passes queue rather than overlap. `syncPremium` combines store and web expiries into `billing/{uid}`.

## Premium accounts and products

1. Create Apple App Store Connect and Google Play billing products, and connect those stores to a RevenueCat project. Use **consumable, non-subscription** products with the same IDs on each platform:

| Product | Access from purchase time | Price decision |
| --- | --- | --- |
| `muse_premium_day` | 24 hours | ₹20 requested |
| `muse_premium_week` | 7 × 24 hours | ₹119 proposed |
| `muse_premium_month` | 30 × 24 hours | ₹399 proposed |

Confirm available INR price points, tax treatment and weekly/monthly prices in each store before activating those products. The app shows the store's localized price before checkout. Preview amounts never determine the charge. There is no auto-renewal. A pass starts at its store purchase time; passes do not stack. The app disables purchasing while a pass is active, and server status blocks checkout while required verification is incomplete. Simultaneous purchases on multiple devices can overlap; support should handle this case.

2. Use the authenticated Firebase UID as RevenueCat's `appUserID`. Configure restore/transfer behavior to **keep purchases with the original app user ID**. The server's hashed transaction ownership ledger also prevents one transaction granting two accounts. Consumable purchases may not restore from the store after reinstall; retain the same Muse account and offer support recovery. The app includes restore and refresh actions without promising recovery of every consumable.
3. Put public SDK keys in the mobile release environment: `EXPO_PUBLIC_REVENUECAT_ANDROID_KEY` / `EXPO_PUBLIC_REVENUECAT_IOS_KEY`. Rebuild the native app after installing the SDK; Expo Go and Muse Test never enable paid checkout.
4. Store `REVENUECAT_SECRET_KEY`, `REVENUECAT_WEBHOOK_AUTH` (the exact Authorization header) and `REVENUECAT_WEBHOOK_SIGNING_SECRET` in Firebase Secret Manager. Enable HMAC signing and send events to `revenueCatWebhook`. It verifies authorization and the signature over the raw body with a five-minute tolerance, then re-reads RevenueCat's subscriber data for purchases, refunds and transfers. Replays do not add days. The hashed ownership tombstone remains after account deletion to prevent reusing a purchase; decide and document its retention period before launch.
5. Set `MUSE_BILLING_ENABLED=true` only after real store sandbox QA. Sandbox purchases never grant production Premium; `MUSE_BILLING_SANDBOX=true` can grant them only in the Functions emulator. Purchases cannot be enabled by a mobile profile field or a successful SDK response alone.
6. The backend cache grants extras only while a pass is unexpired and was checked within ten minutes. App discovery and Premium screens refresh every five minutes while mounted. A signed refund webhook updates the cache; a missed webhook can leave extras for up to ten minutes. Expired/stale checks revert to free limits without denying basic matching. API outages prevent a new grant; users can refresh after recovery.

Primary references: [RevenueCat Expo](https://www.revenuecat.com/docs/getting-started/installation/expo), [consumable handling](https://www.revenuecat.com/docs/platform-resources/non-subscriptions), [signed webhooks and reconciliation](https://www.revenuecat.com/docs/integrations/webhooks).

## AI and optional calls

Set `ANTHROPIC_API_KEY` in Secret Manager; the discovery, suggestion and message-moderation functions bind that secret explicitly. `MUSE_MATCHING_MODEL` defaults to `claude-haiku-5-5`. An enabled toggle without a valid provider key still works through the rules fallback. Review provider retention, privacy disclosures and regional consent requirements before enabling live processing.

For calls, configure `JAAS_APP_ID`, `JAAS_KEY_ID` and the secret `JAAS_PRIVATE_KEY`, then set `EXPO_PUBLIC_CALL_DOMAIN=8x8.vc` and regenerate native permissions through Expo prebuild. Anonymous/self-hosted rooms are no longer enabled by this setting. Confirm room creation, both members joining, token expiry, blocks and unmatches on physical iOS and Android devices before offering calls. [JaaS token reference](https://developer.8x8.com/jaas/docs/api-keys-jwt/).

## Deployment and remaining acceptance work

Firebase requires every bound secret to exist before deployment. If an integration is intentionally disabled, use the literal `disabled` as its temporary secret value, keep its enable flag false and replace it before live QA. The code treats `disabled` API/private keys as unavailable; it is not a credential. Never use that value as a live webhook authorization/signing secret. Deploy rules, indexes and functions together after configuring secrets. Deploying this change without a working verification provider will block dating interaction by default. Existing users need a new bound photo check. Public launch also needs staffed moderation/appeals, Hindi/Hinglish and accessibility research, abuse/OTP strategy, privacy/legal updates and verified store products. Do not describe the app as perfect or proven safer than competitors without user evidence.

Local tests cover policy enforcement, modified/expired approvals, all-four-member message access, immutable Storage paths, moderator claims, forged paid access, provider/HMAC parsers, consent and fallback. Live Didit, live Claude matching, store purchase/refund/restore and JaaS end-to-end flows require credentials and provider QA. iOS has not been built or tested in this iteration.
